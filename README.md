# Telegram-бот расписания БГМУ

Бот получает расписание из https://bgmu-time.ru/api.php. Пользователь один раз
привязывает свою группу и подгруппу, затем открывает нужный день одним нажатием.
Расписание всех групп текущего семестра скачивается
одним фоновым заданием в 07:00 по Уфе и сохраняется в `.data/schedule.sqlite3`.
**Все команды пользователей и обоих ботов читают только локальную копию.**
Ни отсутствие записи, ни истечение кэша, ни повторный запрос пользователя
не вызывают обращения к сайту. Настройки сохраняются отдельно в SQLite.

## Возможности

- Главная с кнопками «Сегодня», «Завтра», «Неделя», «Выбрать дату» и «Моя группа».
- Быстрая привязка: написать `Л-101` → выбрать группу → подгруппу.
- Альтернативно: факультет → курс → группа; текущий учебный период определяется автоматически.
- У каждого пользователя своя сохранённая группа, которую можно заменить или отвязать.
- Недельное расписание с понедельника по воскресенье; переходы между неделями.
- Администратор `@Timur0_15`: отдельная кнопка обновления и команда `/refresh`.
- Ежедневное обновление в **07:00 по Уфе** с заменой предыдущего кэша.
- В «Других расписаниях»: группы.
- Учебный год и осенний/весенний семестр.
- Для групп: факультет → курс → группа → подгруппа, если она есть.
- Выбор даты календарём или сообщением `ДД.ММ.ГГГГ` / `ГГГГ-ММ-ДД`.
- Поиск по части названия и страницы больших списков.
- Время, тип и предмет занятия, группы/подгруппы, преподаватели и места.
- Обновление с сайта, возврат к выбору и ссылка на выбранное расписание.
- Пометки сайта об устаревшей копии и записях без точной даты.

Время занятий — **Уфа, UTC+5**. Локальная база содержит все сущности текущего
семестра, а не только сохранённые пользователями группы. В памяти держится до
128 прочитанных ответов; вытесненные данные читаются с диска, а не с сайта.
Поэтому число групп не ограничено размером кэша.

Полная загрузка выполняется с **не более чем 4 параллельными запросами**,
интервал между началами запросов — не менее 0,25 секунды (не более 4 запросов/с).
Попытка ограничена 15 минутами: при превышении времени загрузка отменяется,
незавершённая база удаляется, предыдущая рабочая копия остаётся. При медленном
ответе сайта успешное завершение в этот срок не гарантируется.
Пока она идёт, пользователи продолжают получать старую копию. Новая база становится
рабочей атомарно только после успешной загрузки всех каталогов и расписаний.
При сбое старые данные сохраняются и показываются с предупреждением.

При первом запуске выполняется первоначальная загрузка. При последующих
перезапусках используется готовая база; если пропущено обновление в 07:00,
фоновой задачей выполняется один догоняющий запуск. Попытка за текущий суточный
период записывается на диск до обращения к сайту: ошибка и повторные перезапуски
не запускают бесконечные повторные скачивания. Следующая автоматическая попытка —
в следующем периоде 07:00; владелец может выполнить ручное обновление раньше.
Первоначальная полная загрузка может занять десятки минут, в зависимости от
числа сущностей сайта. До её завершения новые пользователи получают сообщение,
что локальная копия ещё готовится, без дополнительных запросов к сайту.

Принудительное полное обновление и обновление выбранного курса доступны только
владельцу. Это единственное исключение из автоматического ежедневного режима.
Сам сайт может возвращать собственную устаревшую копию; очистить его кэш бот не может.

## Запуск на BotHost

Нужен Python **3.12**. Загрузите файлы проекта или выберите ветку
`codex/admin-broadcasts` при подключении репозитория, если BotHost позволяет
указать ветку. Для подключения через `main` сначала объедините эту ветку с `main`.

Установите зависимости:

```bash
python -m pip install --require-hashes -r requirements.txt
```

В настройках окружения хостинга задайте `TELEGRAM_BOT_TOKEN` — токен бота,
созданного через `@BotFather`. Значение вводится в защищённых настройках,
не добавляется в Git и не отправляется в чат. `.env.example` описывает имена
переменных; автоматическая загрузка `.env` не используется.

Дополнительные настройки:

- `BGMU_DATA_DIR` — постоянный приватный каталог, по умолчанию `.data`.
  Файл `preferences.sqlite3` содержит Telegram ID и выбор группы, без занятий.
  Сохраняйте этот каталог при перезапуске/обновлении BotHost и не публикуйте его в Git.
- `ADMIN_USERNAME` — `Timur0_15` по умолчанию. Проверяется настоящий username
  отправителя Telegram; имя профиля не даёт права на обновление. Если username
  перейдёт другому аккаунту, право перейдёт вместе с ним — это выбранная привязка по тегу.

Файл запуска — `main.py`, команда:

```bash
python main.py
```

Бот использует long polling: домен, веб-сервер и входящий порт не требуются.
На один токен запускается один процесс. Команды: `/start`, `/menu`, `/group`,
`/help`, `/refresh` (для администратора). Утренний планировщик работает внутри
этого процесса: для ежедневного обновления бот должен постоянно работать.
Временный тест GitHub Actions ограничен по времени и не заменяет постоянный
BotHost; SQLite между отдельными временными запусками Actions не переносится.

## Прокси

Опциональная переменная `BGMU_PROXY_URL` задаётся процессу через настройки
окружения. Поддерживаются следующие форматы:

```text
http://LOGIN:PASSWORD@HOST:PORT
https://LOGIN:PASSWORD@HOST:PORT
socks5://LOGIN:PASSWORD@HOST:PORT
```

Специальные символы URL в логине/пароле нужно percent-encode. Через этот
прокси идут только запросы сайта; Telegram сохраняет собственный маршрут.
Проверка TLS включена. Прокси не обязателен: при исследовании сайта стандартный
GitHub runner получил страницу, каталоги и расписания напрямую.

Проверка на самом BotHost после установки зависимостей:

```bash
python -m bgmu_bot.check_source --live
```

Команда проверяет реальные каталоги, группы, подгруппы,
получение занятий и формирование сообщений. Токен Telegram ей не требуется;
отправка сообщений в Telegram проверяется отдельно после запуска бота.
При `--report /tmp/bgmu-live.json` сохраняются только результаты и счётчики,
а не содержимое занятий.

## Разработка

```bash
uv sync --locked
uv run --locked python -m pytest -q
uv run --locked python main.py
```

`uv.lock` фиксирует зависимости разработки, `requirements.txt` предназначен
для обычного pip-хостинга. После изменения зависимостей:

```bash
uv lock
uv export --locked --no-dev --no-emit-project --format requirements-txt --output-file requirements.txt
```

Тесты покрывают сохранение и изоляцию личных групп, быстрые кнопки, права администратора,
планирование на 07:00 по Уфе, атомарную замену кэша и сбои обновления,
API источника, факультеты и курсы, сохранение общих занятий
при фильтрации подгрупп, различия преподавателей/мест, пагинацию и поиск,
даты, ошибки, повторные запросы и ограничения сообщений Telegram.

## Как исследовали сайт

В облачной среде разработки прямой запрос блокировался шлюзом. Ветка
[codex/bgmu-source-inspection](https://github.com/optimur24-gif/raspisanir-bgmu/tree/codex/bgmu-source-inspection)
содержит диагностический GitHub Actions workflow и исходники публичного
интерфейса сайта. Runner получил их и вернул результат коммитом через Git.

Рабочий бот использует API сайта напрямую. Workflow
`.github/workflows/verify-bgmu-bot.yml` запускает тесты и проверку реального API
при изменении кода в ветке бота; отчёт `verification/live.json` содержит только
проверенные сценарии и их счётчики. Наличие старого отчёта не означает, что
последний запуск прошёл: проверяйте также статус соответствующего Actions run.

## Расписание в общих чатах

Добавьте общего бота в группу или супергруппу. Он спросит, какую учебную группу
закрепить, и покажет обозначения `Л-`, `П-` и остальные **из текущего каталога сайта**.
Далее выбираются полный номер группы и подгруппа. На кнопках показываются названия,
а не внутренние числовые ID сайта. Настройку подтверждает администратор Telegram-чата;
она общая для чата и не меняет личные группы участников.

Если бот уже был добавлен, администратор запускает `/group`. Быстрая настройка:
`/group Л-101`. Типы и списки групп имеют пагинацию. Группа и настройки рассылки
сохраняются в той же приватной `preferences.sqlite3`, что и личные настройки.

Любой участник может написать:

| Команда | Ответ |
| --- | --- |
| `сегодня`, `завтра` | Расписание закреплённой за чатом группы |
| `расписание недели`, `расписание на неделю` | Текущая неделя, понедельник–воскресенье |
| `следующая неделя` | Следующая неделя |
| `расписание на среду` | Ближайшая среда, включая сегодня |
| `расписание на 25.10`, `расписание на 25.10.2026` | Дата; без года используется текущий год |
| `до конца`, `до конца пары` | Минуты до окончания текущей пары |
| `сейчас`, `следующая пара` | Текущая или следующая пара |

Те же запросы работают в личке с личной группой. В чате также есть slash-команды
`/today`, `/tomorrow`, `/week`, `/left`, `/schedule 25.10` и `/help`.
Команды, явно адресованные другому боту через `@username`, игнорируются.
На посторонние сообщения и команды модерации общий бот не отвечает.
После предупреждения новые доступные сообщения записываются в журнал чата.

**Обычные сообщения Telegram:** в BotFather выполните `/setprivacy` → выберите
общего бота → `Disable`, затем пере-добавьте его в чат. Другой вариант — сделать
его администратором. При включённом Privacy Mode бот может не получать слова
`сегодня` и `завтра`; slash-команды остаются способом обращения к нему.
Общему боту права бана, удаления сообщений и ограничения участников не нужны.

**Рассылка по Уфе (UTC+5):** каждое утро с 07:30 — расписание на текущий день,
каждый вечер с 20:00 — на следующий. В том числе отправляется явный ответ,
если занятий нет. Планировщик проверяет время раз в минуту и повторяет неудачные
отправки в течение 30 минут. После долгого простоя старые рассылки не догоняются.
В SQLite сохраняются дата/вид отправки, число частей и хеш ответа, без текста
расписания. Завершённая рассылка не повторяется после перезапуска. При сетевой
ошибке после фактической доставки, но до подтверждения Telegram, возможен повтор
неподтверждённой части. Рабочее расписание читается из ежедневной локальной базы без обращений к сайту.

Администратор чата может отключить или включить рассылку:
`/notifications_off` и `/notifications_on`. Команды расписания работают независимо
от рассылки. После удаления бота из чата рассылка прекращается. При преобразовании
обычной группы в супергруппу привязка и отметки рассылок переносятся на новый ID.
Чтобы рассылки работали постоянно, оставьте процесс на BotHost включённым и
сохраняйте каталог данных.

## Исходный бот управления из bot.py

Полный исходный функционал прикреплённого бота перенесён в `restricted_bot/bot.py`:
админ-панель, модерация и варны, объявления, опросы, упоминания, ДЗ и отметки
выполнения, ссылки, события, напоминания, поиск расписания, экспорт CSV/ICS, приветствия, диагностика и резервные копии.
Это **отдельная личность Telegram** с прежними ограничениями; оба бота запускаются
одним процессом из одной папки.
Общий бот расписания не получает эти права управления.

Ограничения закреплены в коде:

- Бот с числовым ID `8591550954`, соответствующий токену из прикреплённого файла.
- Управляемый чат `-5519960135`.
- Главный администратор `1153815035`, как в оригинале; назначенные им заместители
  хранятся в исходной базе. Личная админ-панель остаётся доступна этим администраторам.
- Другие групповые чаты отсекаются до обработчиков. Дополнительная проверка
  исходящих Telegram API-вызовов запрещает управление другим групповым чатом.
- Токен другого бота не позволяет запустить этот процесс. Проверяются ID из
  конфигурации и реальный `getMe` при запуске.

Для обоих ботов на одном BotHost используйте одну команду:

```bash
python main.py
```

Задайте обе переменные: `TELEGRAM_BOT_TOKEN` — общий бот,
`RESTRICTED_BOT_TOKEN` — исходный бот. Если задан только первый токен,
работает только общий бот. `python -m restricted_bot` остаётся совместимым
вариантом отдельного запуска исходного бота, который также получает П-114 с сайта,
но для общего источника в одном процессе используйте `python main.py`.

Переменная `RESTRICTED_BOT_TOKEN` должна содержать токен именно исходного бота,
введённый в защищённых настройках хостинга. Токен из загрузки не публикуется в Git.
`DATA_DIR` задаёт отдельный постоянный каталог, по умолчанию `.data/restricted`.
Если есть старая база `bot_data.db` с домашкой и настройками, перенесите её вместе
с резервными копиями в этот каталог перед запуском. Сам загруженный Python-файл
не содержит прежних записей базы. Не запускайте два процесса для одного токена.

Проверка без подключений к Telegram (с корректной переменной исходного бота):

```bash
python -m restricted_bot --check
```

Исходный бот получает **П-114 с сайта через общий источник**; собственная ручная
таблица расписания больше не используется. Утренние/вечерние рассылки, напоминания
о парах, команды, поиск, нагрузка и CSV/ICS читают эти данные. Ручные добавление,
удаление и копирование пар отключены; ДЗ, события, модерация и настройки остаются
доступны. Новые занятия не пишутся в основную базу или резервные копии. Старые
ручные записи не удаляются, но не показываются вместо сайта. При недоступности
сайта показывается предупреждение с предыдущей копией; до первого успешного
получения бот сообщает о недоступности расписания, а не о свободном дне. Если в
закреплённом чате работают оба бота, администратор может отключить рассылку общего
бота через `/notifications_off`, чтобы оставить только одну.


## Общая папка и передача П-114

```text
raspisanir-bgmu/
  main.py                 # единый запуск двух ботов
  bgmu_bot/               # сайт, общий кэш, общий бот
  restricted_bot/         # исходный бот управления
  .data/
    preferences.sqlite3   # группы пользователей и чатов
    schedule.sqlite3      # ежедневная копия всех расписаний
    restricted/           # ДЗ, настройки и резервные копии исходного бота
```

Оба бота используют один `BGMUSource` и один HTTP-клиент. П-114 определяется
по точному названию в текущем каталоге сайта, без фиксации внутреннего ID или
учебного года. Передаётся всё семестровое расписание со всеми подгруппами,
преподавателями и местами; дальнейший выбор дня выполняется без повторного
скачивания всего расписания. Связанный бот проверяет локальные данные раз
в минуту; эти проверки не обращаются к сайту. Ручное `/refresh` и обновление в 07:00
сразу обновляют связанное расписание П-114. Результат передачи виден администратору
в ответе на `/refresh`.

Управление по-прежнему доступно только исходному боту и исходному чату.
Для связанного запуска не нужны пересылка сообщений между ботами, второй
репозиторий или отдельная служба. При ошибке запуска одного из ботов единый процесс
завершается, чтобы хостинг мог корректно перезапустить оба.


## Обновление отдельного курса (администратор общего бота)

Для `@Timur0_15` на главной есть отдельная кнопка **«🎯 Обновить курс»**:
факультет → курс → число групп → «Обновить этот курс». Бот заново запрашивает
с сайта расписания **всех групп выбранного курса**, даже если никто из пользователей
их ещё не сохранял. Данные других курсов сохраняют прежний срок актуальности;
личные привязки и настройки чатов остаются. При ошибке загрузки всего курса
замена не выполняется. Проверка настоящего username выполняется на каждом шаге,
включая подтверждение; скрытые кнопки и поддельные callback-запросы не дают права
на обновление.

Если выбранный курс включает П-114, успешное обновление сразу передаётся
исходному боту. В ответе показываются факультет, курс, количество обновлённых
групп, время по Уфе и предупреждения сайта об устаревших копиях. Бот не может
принудительно очистить собственный кэш сайта. Обновление курса заменяет только
расписания выбранного курса в локальной базе, сохраняя остальные группы. Размер кэша в памяти не ограничивает число сохранённых
групп; повторные пользовательские запросы читают локальную базу.

«Обновить данные» и `/refresh` выполняют полное скачивание двух каталогов — групп
и расписаний всех перечисленных групп текущего семестра.
Автоматическое обновление в 07:00 использует тот же полный режим.


## Единая подача расписания

В личке, общих чатах и исходном боте П-114 ответы и рассылки имеют один формат:

```text
П-114
21.10.2026 · Среда

09:00–10:35 · 🎓 Лекция · Педиатрия
ауд. 101, Корпус 1 · Иванов И.И.

10:50–12:25 · 🧪 Практика · Биология
ауд. 202 · Петрова А.С.
```

В расписании видны тип занятия и день недели. Убраны факультет, семестр, комментарии
и время обновления. Фамилия сохраняется, имя/отчество сокращаются до инициалов.
При разных аудиториях и преподавателях подгрупп сохраняется пометка подгруппы,
чтобы не перепутать пары. Недельный ответ содержит даты, названия дней недели и пары каждого дня.
Предупреждения о недоступности или устаревшей копии показываются при наличии
проблемы; пустой день обозначается явно.


## Админ-панель, пользователи и объявления

В общем боте `/admin` или кнопка «🛠 Админ-панель» доступны только владельцу
с настоящим Telegram username `ADMIN_USERNAME` (по умолчанию `Timur0_15`),
только в личке. Проверка выполняется при каждом нажатии.

- «Пользователи»: имя, актуальный известный @тег, ID, доступность, подписка,
  сохранённая учебная группа, факультет, курс и подгруппа.
  Здесь только пользователи, обращавшиеся к боту в личке; списки участников
  групп бот не выгружает. Если @тега нет, показывается ID.
- «Подключённые чаты»: название, ID, публичная ссылка `t.me`, если есть,
  учебная группа, права бота и кто его добавил, если Telegram сообщил.
  Для закрытых чатов бот не создаёт приглашения. «Проверить права» обновляет
  сведения через Telegram без сообщений администраторам чатов.
- «Новая рассылка»: всем пользователям в личку, всем подключённым группам
  или выбранным группам. После текста показываются предпросмотр и подтверждение.
  Отправка без подтверждения невозможна. Доступны отчёт и остановка.
- `/unsubscribe` (или `/stop`) и `/subscribe` в личке отключают/включают
  объявления владельца. В группах `/announcements_off` и `/announcements_on`
  доступны администраторам чата и не меняют уведомления расписания.

Очередь рассылки хранится в SQLite, отправляет до трёх сообщений за секунду,
учитывает Telegram RetryAfter, блокировки и отписки непосредственно перед отправкой.
При сетевой неопределённости или прерывании запроса сообщение получает статус
«Неподтверждённая доставка» и автоматически не повторяется, чтобы избежать дублей.
Завершённую историю с текстами объявлений владелец удаляет вручную из панели.
Метаданные подключений сохраняются отдельно от журнала. Перед записью новых
сообщений бот отправляет в чат явное предупреждение; без успешной отправки
предупреждения журнал не ведётся. Вложения не скачиваются.

`/start`, `/help` и кнопка «📖 Инструкция» объясняют выбор факультета, курса,
группы, добавление бота в чат и доступные команды. Telegram не сообщает боту
о простом повторном открытии окна — инструкция отправляется по этим действиям.
В обоих ботах действует интервал 2 секунды между запросами пользователя;
владелец освобождён, обычные разговоры в общем чате интервал не расходуют.

Для пяти групп 1 ГБ RAM и 5 ГБ диска должны быть достаточны при обычной нагрузке:
два бота работают в одном процессе, кэш расписаний ограничен, медиа не скачиваются.
Это оценка, а не нагрузочный тест; сохраняйте каталог `.data` между перезапусками
BotHost, иначе привязки, реестр и очередь рассылок будут потеряны. Не запускайте
два экземпляра с одним токеном одновременно.

### Уведомления владельцу о подключениях

`/admin` → «🔔 Уведомления» содержит отдельные переключатели
для пользователей и чатов. По умолчанию оба включены; настройки хранятся
в `.data/preferences.sqlite3` и сохраняются при перезапуске.

После обновления владелец должен один раз отправить `/start` в личке общего
бота: по настоящему `ADMIN_USERNAME` бот запомнит ID получателя уведомлений.
Перед отправкой проверяется соответствие текущего username владельца.
Если владелец ещё не обращался к боту или заблокировал его, уведомление
не доставляется; ошибки доставки не мешают расписанию. Старые подключения
задним числом не рассылаются.

Оповещение о первом обращении пользователя содержит имя, @тег при наличии
и ID; о впервые обнаруженном чате — название, ID, публичную ссылку и сведения
о добавившем, если Telegram их передал. Повторные обращения, перезапуск бота,
изменение прав и повторное добавление известного чата не создают дублей.
Сообщения отправляются только владельцу в личку, не администраторам групп.

### Отключение доступа пользователям и чатам

В личке общего бота: `/admin` → «Пользователи» или «Подключённые чаты» →
кнопка 🔒 с именем/названием → «Подтвердить отключение». После блокировки
эта же карточка предлагает «Восстановить доступ». Действия доступны только
владельцу; отключить себе доступ через панель нельзя.

Блокировка пользователя действует в личке и при его запросах в общих чатах.
Блокировка чата действует для всех участников именно этого чата; их личный
доступ сохраняется. Команды и старые кнопки заблокированы, получатели исключены
из новых и уже поставленных в очередь рассылок, а заблокированные чаты —
из автоматического расписания. Уже переданный Telegram запрос отозвать нельзя.

Блокировки привязаны к числовым ID, сохраняются в `.data/preferences.sqlite3`
и переносятся при превращении группы в супергруппу. Смена @тега, повторный
`/start`, удаление/добавление бота и изменение его прав блокировку не снимают.
Учебная группа, подписки, ДЗ и остальные настройки не удаляются. Это управление
доступом к общему боту; самостоятельный исходный бот П-114 сохраняет свою
существующую систему прав.


### Последние резервные копии настроек и расписания

`/admin` → «💾 Резервные копии» показывает время/размер файлов и позволяет
владельцу скачать их в личку. При стандартных настройках это:

- `.data/backups/settings.sqlite3` — единая копия настроек всех пользователей
  и чатов: привязки групп/подгрупп, подписки, блокировки, настройки владельца,
  известные подключения. Обновляется после изменения этих настроек, регистрации
  нового пользователя/чата и общего/курсового обновления. Очередь объявлений
  и история рассылок исключены из резервной копии, чтобы восстановление
  настроек не отправило старые объявления повторно.
- `.data/backups/schedule.sqlite3` — последняя полная копия ежедневной базы:
  все каталоги и расписания групп текущего семестра.
  Обновляется после полного обновления или успешного обновления курса.
  Вытеснение из кэша не удаляет расписания из базы/копии. Старый формат
  `schedule.json.gz` удаляется после первой успешной записи новой полной копии.
Для каждого типа остаётся **один** файл: запись во временный файл с правами
`0600`, синхронизация на диск и атомарная замена. Настройки копируются средствами
SQLite Backup API с проверкой целостности; накопления копий с датами нет.
Ошибка сайта или записи не удаляет предыдущую исправную копию. Чтение уже
закэшированного расписания не создаёт новую копию.

Для восстановления настроек остановите процесс обоих ботов, скачайте текущую
рабочую базу для сохранности, затем замените `.data/preferences.sqlite3`
файлом `settings.sqlite3` и запустите процесс. Для восстановления расписания
замените `.data/schedule.sqlite3` файлом резервной копии `schedule.sqlite3`.
После запуска бот сразу использует сохранённую базу. Очередь объявлений в копию
настроек не входит; старые объявления после восстановления не отправляются.
Резервирование исходного бота П-114 управляется его прежним разделом отдельно.

Большую копию, превышающую лимит Telegram, скачивайте через файловый менеджер
BotHost из `.data/backups`; бот не загружает её целиком в оперативную память.
Сохраняйте всю папку `.data` на постоянном диске BotHost. Копия на том же диске
защищает от ошибок приложения, но не от потери диска — скачивайте файлы через
админ-панель для внешнего хранения. Токены и пароль прокси в эти копии не входят.


### Известные участники каждого чата

`/admin` → «Подключённые чаты» → «👥 Участники: название чата».
Показываются имя, @тег, числовой ID и известный факт выхода из чата,
с постраничным просмотром. Список доступен только владельцу общего бота
в личке, сохраняется между перезапусками и входит в копию настроек.

Telegram Bot API **не позволяет выгрузить всех участников группы**.
В список попадают только пользователи из доступных боту сообщений/нажатий
и событий входа/выхода, полученных после подключения этой версии бота.
Боты и сообщения от имени канала/анонимного администратора не записываются
как обычные участники. Privacy Mode и права бота влияют на доступные обновления;
молчавшие до подключения пользователи автоматически не обнаруживаются.

«Обновить число и администраторов» запрашивает общее количество участников
и доступный список администраторов; анонимные администраторы исключены.
Общее число включает участников, которых бот не знает (в том числе ботов),
поэтому оно может отличаться от числа известных записей. Показанный статус
не является текущей проверкой членства: события выхода могут быть недоступны.
Ошибка Telegram не удаляет ранее известные записи.

В базе настроек сохраняются поля профиля и принадлежность к наблюдаемому чату.
Открытый журнал новых сообщений хранится отдельно, после предупреждения в чате;
старые сообщения до предупреждения и файлы вложений не архивируются.
Записи участников не создают личную подписку и не включаются в личную рассылку,
пока человек сам не обратится к боту. Просмотр выполняется без сообщений в группу.


### Выбранные группы пользователей и ошибки ежедневного обновления

`/admin` → «Пользователи» показывает для каждого зарегистрированного пользователя
его сохранённую учебную группу, факультет, курс и подгруппу. Если привязки нет,
указано «Учебная группа: не выбрана». Просмотр доступен только владельцу
`ADMIN_USERNAME` (`Timur0_15`) в личке бота, с повторной проверкой роли на каждом
нажатии; в групповые чаты эта информация не отправляется. Чтение выбранных групп
выполняется из настроек и не обращается к сайту.

При ошибке первоначальной/ежедневной загрузки владелец получает личное сообщение
с временем по Уфе, причиной и временем предыдущей рабочей копии, если она есть.
Старое расписание остаётся доступным; дополнительные запросы к сайту из-за
уведомлений или повторных команд пользователей не выполняются. Ручные ошибки
полного/курсового обновления также отображаются владельцу в ответе на его действие.

`/admin` → «🔔 Уведомления» → «Ошибки обновления» — отдельный переключатель,
по умолчанию включённый; настройки уведомлений о новых пользователях/чатах
на него не влияют. После обновления один раз отправьте `/start` со своего аккаунта,
если ID владельца ещё не был привязан. Если получатель пока неизвестен или
Telegram не доставил сообщение, последняя ошибка сохраняется и отправляется
при следующем обращении владельца. Успешно доставленное уведомление повторно
не отправляется; проверяется соответствие текущего Telegram username владельца.


### Диагностика ошибок обновления на хостинге

`/admin` → «🩺 Статус обновления» показывает последнюю рабочую копию, число
загруженных расписаний, название скачиваемой группы,
прогресс текущего раздела (например, 17/652), длительность попытки и последние
шаги с временем по Уфе. Видны ожидание интервала между запросами, обращение к
сайту, проверка ответа, запись данных, проверка целостности базы, замена копии
и создание бэкапа. Ошибка бэкапа отображается отдельно от результата загрузки.
При сбое сохраняются последний этап, запрос и причина ошибки.
Кнопка «🔄 Обновить экран» показывает актуальные сведения; экран доступен только владельцу.
Просмотр и обновление этого экрана не обращаются к сайту. При ручном обновлении
в ответе теперь есть строка «Причина» и этап (период, каталог, расписание с ID,
сохранение файла). Ошибки диска и SQLite отличаются от HTTP/сетевых ошибок.

В логах остаются начало полной загрузки, размеры каталогов, прогресс каждые
50 расписаний и результат. Ежесекундные сообщения успешного запуска служебных
задач APScheduler скрыты; предупреждения и ошибки остаются. Токены, URL с
паролями и произвольные тексты исключений в диагностике не выводятся.

При неудачном обновлении ответы сайта с `meta: null` в предыдущей копии
теперь корректно открываются с предупреждением, без ошибки обработки метаданных.
Диагностика GitHub Actions в `check-daily-snapshot.yml` выполняет только
распределённую выборку: не является подтверждением успешной загрузки всех
сущностей или доступности сайта с IP BotHost. Telegram-ботов она не запускает.

Отдельные разделы преподавателей и аудиторий отключены: их каталоги и расписания не
скачиваются при обновлении. Преподаватели и номера аудиторий в занятиях групп остаются.
После обновления кода уже начатую загрузку нужно запустить заново; новая
полная копия будет содержать только группы.


### Открытый журнал чатов

Общий бот перед записью отправляет в каждый подключённый чат предупреждение:
что сохраняется, кому доступен журнал и что для остановки записи нужно удалить
бота. Бот пытается закрепить предупреждение; Telegram разрешает это только
при достаточных правах, а администраторы могут удалить или открепить сообщение.
При входе новых участников предупреждение повторяется. Для уже подключённых
чатов эта версия отправит предупреждение при запуске или первом новом сообщении.
Если отправка не удалась, запись не начинается; повторная попытка — не чаще раза в минуту.

Записываются только сообщения с ID позже предупреждения, полученные через Bot API:
автор (@тег или имя и ID), время по Уфе, текст. Для фото, видео, голосовых и других
вложений остаются пометка и подпись; файлы не скачиваются. Доступные правки
добавляются отдельными строками, старые сообщения до предупреждения исключены.
Нет выгрузки старой истории, восстановления удалённых сообщений или записи личных
сообщений боту. Telegram не передаёт сообщения других ботов; Privacy Mode и
права бота могут ограничить доступные сообщения. Чтобы получать обычную переписку,
нужен отключённый Privacy Mode с повторным добавлением бота либо статус администратора.

Файлы: `.data/chat-journals/chat_<ID>.txt` — по одному на чат, UTF-8;
`state.sqlite3` — состояние предупреждений и индекс для защиты от повторных обновлений.
Папка имеет права `0700`, файлы — `0600`. Журналы не входят в бэкапы настроек
и расписания. Сохраняйте всю `.data` между перезапусками. Автоматической очистки нет:
место зависит от объёма переписки, без сохранения файлов вложений.

Только владелец, в личке: `/admin` → «Подключённые чаты» → «Журнал» —
последние записи, скачивание TXT, очистка выбранного журнала с подтверждением.
В корне панели можно вручную очистить все журналы с подтверждением.
Очистка не отменяет предупреждение и не отключает запись новых сообщений.
Большие журналы (свыше 49 МиБ) скачиваются через файлы хостинга.
Отдельного переключателя записи нет. Отписка от рассылки и запрет команд
не отключают журнал; удаление бота из чата останавливает запись.

Журнал реализован в `bgmu_bot/journal.py`: `JournalNotices` отправляет
предупреждения, `JournalRuntime` обрабатывает сбои уведомлений, а `JournalObserver`
записывает только сообщения с подтверждённым уведомлением. `ui.py` подключает эту
реализацию. Файлы `journal_runtime.py` и `journal_notice.py` удалены.

При сбое уведомления текущий update не записывается, даже если в базе есть старое
предупреждение. Причина отображается в админ-панели без текста исключения.
Запуск, инструкция и задачи расписания продолжают работать. При повторном входе
бота и изменении текста предупреждения чат уведомляется заново. Одновременные
уведомления одного чата сериализованы; повторные неудачные отправки ограничены
по частоте. Второй polling с тем же токеном запускать нельзя.

## Локальный запуск после импорта

Установите Python 3.12 и uv, затем выполните `uv sync --locked` и `./run.sh`.
Скрипт запуска читает локальный `.env` (исключён из Git), затем запускает обоих
ботов через `main.py`. `TELEGRAM_BOT_TOKEN` используется для бота расписания,
`RESTRICTED_BOT_TOKEN` — для бота управления группой с ID бота `8591550954`.
Настройки и секреты на другом сервере нужно задать заново по `.env.example`.

`bgmu_bot/ui.py` основан на отдельно приложенном файле; встроенная реализация
журнала заменена подключением полной реализации из `journal.py`.
Проверка: `uv run --locked python -m pytest -q` — 194 passed, 8 предупреждений
библиотеки python-telegram-bot об устаревающем представлении `retry_after`.
Тесты используют тестовый транспорт; работа с реальным Telegram не проверялась.
Архивные `SHA256SUMS.txt` и `verification/` описывают исходный архив, а не
результат этой замены и локальных настроек.

## Пробный запуск на GitHub Actions

Workflow **Run bots and check schedules** запускает тесты, проверяет реальные
расписания групп (включая подгруппы, преподавателей и места занятий), резервное
копирование и затем обоих
ботов. Перед запуском задайте в **Settings → Secrets and variables → Actions**
секреты `TELEGRAM_BOT_TOKEN` и `RESTRICTED_BOT_TOKEN`; `BGMU_PROXY_URL` нужен только
если сайт недоступен с runner. Значения токенов не добавляйте в файлы репозитория.

После публикации workflow откройте **Actions → Run bots and check schedules →
Run workflow**. Выберите ветку `main` и длительность 5–120 минут
(по умолчанию 15). Логи видны во время выполнения: откройте запуск →
**check-and-run → Run both bots (live console)**. Предыдущие шаги показывают
результаты тестов, загрузки расписаний и проверки конфигурации. Кнопка
**Cancel workflow** останавливает ботов. После выполнения отчёты и консоль
доступны в **Artifacts → bot-diagnostics-…**.

GitHub Actions даёт временный процесс: после завершения задания боты остановятся,
а локальные данные runner не сохранятся. Не запускайте одновременно другую копию
этих же ботов. Для постоянной работы и сохранения настроек/журналов используйте
сервер с постоянной папкой `.data`; стартуйте `./run.sh` в его терминале.

### Полная загрузка расписания

`uv run --locked python -m tools.fetch_schedule` скачивает расписания **всех** групп
текущего каталога в `.data/schedule.sqlite3`, создаёт резервную копию и проверяет
каждую группу без HTTP-запросов, включая передачу П-114 боту управления.
При ошибке загрузки предыдущая база остаётся на месте. Итог и счётчики записываются
в `.runtime/full-schedule.json`. Команда использует обычную проверку TLS и
ограничение частоты запросов, встроенное в адаптер.

Workflow выполняет полную загрузку перед стартом ботов. В Artifacts →
`bot-diagnostics-…` сохраняются `schedule.sqlite3`, его копия из `backups/` и
`full-schedule.json`; данные пользователей и журналы в архив не включаются.
После скачивания артефакта рабочую базу можно положить в `.data/schedule.sqlite3`
на сервере. Автоматический запуск при push теперь держит ботов до 120 минут;
при ручном запуске длительность задаётся в форме.

Если значения двух GitHub Secrets перепутаны, workflow определяет роли по ID
ботов и передаёт токены следующим шагам через защищённый `GITHUB_ENV`. Лишние
кавычки или вставленное `NAME=…` также допускаются. Токены других ботов и
противоречащие значения отклоняются; ограничение личности бота управления
не снимается. Нормализованные значения маскируются runner до следующих шагов.
Артефакт `full-schedule-…` сохраняется сразу после полной проверки расписания,
до запуска ботов, и доступен для скачивания во время их работы.

### Группа бота управления

Текущая Telegram-группа: `-5519960135`. `GROUP_CHAT_ID` задаётся в `.env` или
переменных процесса; GitHub Actions читает Repository variable `GROUP_CHAT_ID`
и использует указанный ID, если переменная отсутствует. При смене ID нужен
перезапуск. Проверка входящих событий и исходящих сообщений использует одну
настройку: команды управления не распространяются на остальные группы.
Бот `@hsthseth_bot` должен быть администратором для модерации и закрепления.

После перезапуска workflow может восстановить базу из артефакта предыдущего
запуска того же репозитория в `main`. `--reuse-recent` разрешает повторно
использовать полную базу не старше 10 минут и заново проверяет каждую группу
без HTTP. Старые, отсутствующие и нечитаемые метаданные не отменяют полную
загрузку с сайта. Это позволяет применить настройку группы без повторного
скачивания только что проверенных 652 расписаний.
